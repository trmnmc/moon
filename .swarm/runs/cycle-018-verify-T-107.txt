Reading of the matrix:

- The PRE-MERGE column is the load-bearing one. Six mutants that make a shipped success
  mode write to stderr sail straight through the old suite. That is the gap, measured
  rather than asserted, and it confirms the item's premise: `run()` calls execFileSync
  with no stdio override, so stderr was inherited by the test process and never captured
  on any passing path.
- M1-M5 are per-mode. They are what distinguishes a real five-mode loop from a test that
  spawns the default mode and calls it coverage: a single-mode test would kill M0 and M5
  and let M1-M4 through. All five modes named in the acceptance are individually covered.
- M6 is the honest negative. A mode exiting non-zero while staying silent was ALREADY
  caught before this item, because execFileSync throws on a non-zero exit. So the new
  test's `assert.equal(result.status, 0, ...)` is defensive redundancy, not new coverage.
  It is not a defect — it keeps the assertion honest if a helper is ever rewritten — but
  it must not be reported as surface this item closed. Recorded here so the ledger is
  accurate.
